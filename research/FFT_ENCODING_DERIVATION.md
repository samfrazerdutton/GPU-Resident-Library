# FFT-based CKKS canonical-embedding encode/decode — derivation, implementation, and verification

GOD PROMPT "CKKS PHASE 12". This document records the mathematical
derivation, implementation, and numerical/cryptographic verification of
`src/encode_fft.cpp`'s `encode_host_fft`/`decode_host_fft`, the O(N log N)
replacement for `src/encode.cpp`'s O(N²) `encode_host`/`decode_host`
(Phase 11's `std::thread`-parallelized version, still present as the
reference/fallback). See `research/EXPERIMENT_LEDGER.md` entry #45 for
the experiment-ledger summary and benchmark results.

## 1. The exact convention already in this repository (authoritative)

Transcribed directly from `src/encode.cpp`'s own header comment and
code, unchanged by this round:

```
M = 2N, S = N/2
tw_enc[t] = exp(-i*pi*t/N),   t = 0..M-1
tw_dec[t] = exp(+i*pi*t/N)
r[k] = 5^k mod M,             k = 0..S-1

encode: m[j] = round( (2*Delta/N) * Re( sum_{k=0}^{S-1} z[k] * tw_enc[(j*r[k]) % M] ) )
decode: z[k] = (1/Delta)      * sum_{j=0}^{N-1}  m[j] * tw_dec[(j*r[k]) % M]
```

### Mapping every item the governing directive asked for

- **Ring dimension `n`/`N`**: `N` is the CKKS polynomial ring dimension
  (the ring is `R[X]/(X^N+1)`, a power of 2 everywhere in this
  codebase — confirmed by every call site, which always derives `N`
  from `native_primes`'s own NTT-friendliness requirement `q ≡ 1 (mod
  2n)`). This file's parameter is literally called `N` in
  `encode_host`/`decode_host`'s own signature — there is no separate
  "n vs N" distinction in this implementation (unlike some papers that
  use lowercase `n` for a different quantity); this document uses `N`
  throughout to match the code exactly.
- **Number of complex slots / conjugate symmetry**: `S = N/2` complex
  slots. A real polynomial of degree `<N` has `N` real degrees of
  freedom; the canonical embedding packs them as `N/2` independent
  complex numbers (2 real DOF each) by exploiting conjugate symmetry
  (see §2) — this is the standard CKKS slot count, matching OpenFHE/
  SEAL exactly.
- **Primitive roots and indexing**: the natural root of this transform
  is `ζ = e^{iπ/N}`, a primitive `2N`-th root of unity (NOT an N-th
  root — this is a *negacyclic*-structured transform, matching the
  ring `X^N+1`, not `X^N-1`). `tw_enc[t] = ζ^{-t}`, `tw_dec[t] = ζ^{t}`
  — a single length-`M=2N` table, indexed by `t mod M`.
- **The `5^k mod 2N` permutation**: `(Z/2NZ)*` (the group of units mod
  `2N`, for `2N` a power of 2 ≥ 8) has order exactly `N` and is
  generated by `{-1, 5}` as `Z/2 × Z/(N/2)` — `5` has multiplicative
  order `N/2` mod `2N`. The set `{r_k = 5^k mod 2N : k=0..N/2-1}`
  enumerates exactly ONE representative from each of the `N/2`
  conjugate pairs `{t, 2N-t}` among the `N` units mod `2N` — this is
  the standard CKKS/BGV "rotation group" slot-indexing convention
  (identical to OpenFHE's own choice of generator 5), **not** a
  textbook power-of-2 bit-reversal permutation; the two must not be
  conflated (see §3).
- **Direction of encode vs. decode**: `decode` evaluates the integer
  coefficient polynomial `m(X) = Σ_j m_j X^j` at `ζ^{r_k}` for each
  slot `k` (the forward canonical embedding `σ`); `encode` computes the
  unique integer polynomial whose canonical embedding is closest to
  the target scaled slot vector (the inverse embedding `σ⁻¹`, i.e.
  `encode ≈ σ⁻¹(Δ·z)` rounded to integers).
- **Normalization**: `decode` divides by `Delta` once. `encode`
  multiplies by `2·Delta/N`; §2 shows this factor of 2 is NOT a
  mismatch with decode's single `1/Delta` — it is required because
  encode's sum folds `S=N/2` independent slots plus their `S` implicit
  conjugates into one real sum via `2·Re(...)`, while decode reads
  back a single (already-real-valued-after-summing) slot directly.
- **Real-input extension**: callers pass `std::complex<double>` slots;
  real-only inputs simply have `.imag()==0` — the same formula handles
  both (confirmed in testing, §5, with both real-only and genuinely
  complex slot vectors).
- **Complex slot → coefficient mapping**: see §2's full derivation —
  slot `k` lands at frequency index `r_k` (and its conjugate at
  `2N-r_k`) of the *virtual* length-`2N` DFT of the zero-padded
  coefficient array; the mapping is NOT a simple interleaving or
  bit-reversal, it is this `5^k`-indexed set.
- **Coefficient ordering**: standard — `m[0..N-1]` are the polynomial's
  coefficients in increasing power of `X`, exactly as `src/encode.cpp`
  already stores them; unchanged by this round.
- **FFT sign convention**: this document fixes the convention
  explicitly as `X[t] = Σ_j x[j]·e^{-2πijt/M}` (forward DFT, negative
  exponent — the same convention `numpy.fft.fft` uses, confirmed by
  cross-checking against it in §4) to avoid any ambiguity when
  implementing the new C++ FFT kernel.
- **Scaling, permutation, conjugation operations**: all derived
  explicitly in §2 and §3, and verified both symbolically (against an
  independent tool, numpy) and numerically (against the existing
  O(N²) code) before any C++ was written — see §4 and §5.

## 2. Derivation: why a single size-`M=2N` FFT suffices

Let `ζ = e^{iπ/N} = e^{2πi/M}` (`M=2N`), a primitive `M`-th root of
unity. For the integer-coefficient polynomial `m(X) = Σ_{j=0}^{N-1}
m_j X^j`, decode's own sum is *exactly*:

```
decode's sum = Σ_j m_j · ζ^{j·r_k} = m(ζ^{r_k})
```

i.e. **decode is "evaluate `m` at `ζ^{r_k}`, for `k=0..N/2-1`"** — the
canonical embedding `σ`, restricted to one representative of each
conjugate pair.

Zero-pad `m`'s `N` coefficients to length `M=2N` (append `N` zeros).
Using the standard forward-DFT convention `X[t] = Σ_{j=0}^{M-1}
x[j]·e^{-2πijt/M}` (matching `numpy.fft.fft`):

```
X[t] = Σ_{j=0}^{N-1} m_j · e^{-2πijt/M} = Σ_j m_j · e^{-iπjt/N} = Σ_j m_j · (ζ^{-t})^j = m(ζ^{-t})
```

So **a single size-`M` FFT of the zero-padded coefficient array gives
`m` evaluated at every power of `ζ`** (as `t` ranges `0..M-1`, `ζ^{-t}`
ranges over every `M`-th root of unity exactly once). Decode therefore
reduces to one FFT plus a **gather**: we want `m(ζ^{r_k})`, i.e. the
bin where `-t ≡ r_k (mod M)`, i.e. `t = (M - r_k) mod M`:

```
z_k = X[(M - r_k) % M] / Delta,   k = 0..N/2-1
```

### Encode (the inverse direction)

Given target slots `z_k`, construct a length-`M` array `Z` representing
the *desired* canonical embedding of `Δ·m` directly at the bins decode
would read from, plus the conjugate bin forced by `m`'s realness:

```
Z[(M - r_k) % M] = z_k         (the bin decode's gather would read)
Z[r_k]            = conj(z_k)   (its conjugate pair — forced by realness)
Z[t] = 0  for every other t     (there are N-S = N/2 such pairs of zero bins; m has only N real DOF total)
```

Take the **unnormalized** inverse DFT `x[j] = Σ_t Z[t]·e^{+2πijt/M}`
(no `1/M` factor). Substituting the scatter above, each of the `N/2`
conjugate pairs contributes:

```
z_k · e^{+2πij(M-r_k)/M} + conj(z_k) · e^{+2πij·r_k/M}
  = z_k · e^{-2πij r_k/M} + conj(z_k) · e^{+2πij r_k/M}
  = 2 · Re( z_k · e^{-iπj r_k/N} )
```

so `x[j] = 2 · Σ_k Re(z_k·e^{-iπjr_k/N})` — **exactly twice** the
quantity encode's own formula calls `Re(Σ_k z_k·tw_enc[...])`. Since
encode's own scale factor is `2·Delta/N`, applying it to `x[j]/2` (not
`x[j]` directly) recovers the exact formula — equivalently, applying
`Delta/N` (not `2·Delta/N`) directly to `x[j]`:

```
m_j = round( (Delta/N) · Re(x[j]) ),   j = 0..N-1   (only the first N of M outputs are used)
```

This `Delta/N` (not `2·Delta/N`) scale, and the `conj(z_k)` placement
at `r_k` rather than `(M-r_k)%M`, were **derived on paper first, then
independently confirmed to match `src/encode.cpp`'s own formula to
*zero* error** (not merely small error) via the Python/numpy prototype
in §4 — the factor-of-2 relationship was not assumed, it fell out of
substituting the scatter into the unnormalized inverse-DFT sum above,
and the numpy check caught an initial factor-of-2 mistake before any
C++ was written (see §4's own note).

### Why this is correct by construction, not merely plausible

This "zero-pad to `2N`, run a standard size-`2N` FFT, gather/scatter by
the `(M-r_k)%M` / `r_k` index pair" approach requires **no new
mathematical object** beyond a textbook DFT and the SAME `r_k` array
`src/encode.cpp` already computes — there is no discrete-logarithm
computation, no bit-reversal-vs-5-adic-permutation confusion, and no
assumption that evaluation at `ζ^t` for arbitrary `t` has any special
structure beyond "it's one bin of a size-`M` DFT of a zero-padded
array." The only two facts used are (a) the standard DFT-of-zero-padded-
signal identity `X[t] = x(ζ^{-t})` for any root of unity `ζ`, and (b)
`m` has real coefficients, so its canonical-embedding values at
conjugate-paired evaluation points are themselves complex conjugates.
Both are elementary and independently checkable (and were checked,
§4). This is deliberately the **simplest correct construction**, at
the cost of a 2x constant-factor overhead (operating on `M=2N`-length
arrays when `N` real degrees of freedom are the true information
content) relative to a tighter N-point negacyclic-twisted FFT — a
trade this round makes deliberately, per the governing directive's own
"evaluate the simplest correct approach first" instruction (§7 of the
Phase 12 prompt). The O(N log N) vs. O(N²) asymptotic win dominates
this constant factor at every N this project targets (confirmed in
§6's benchmarks: 31-61x faster, far more than a mere 2x loss from the
tighter construction could ever cost).

## 3. Why this is NOT the same permutation as a textbook FFT's bit-reversal

A standard radix-2 Cooley-Tukey FFT's bit-reversal permutation reorders
INPUT (or output) elements of a length-`M` array among themselves,
based on `M`'s own binary structure — it has nothing to do with CKKS's
slot semantics. The `r_k = 5^k mod M` array is a completely different,
CKKS-specific GATHER/SCATTER applied to a small subset (`N/2` of `M`
total bins) of an *already-computed* standard FFT's output/input, to
select which frequency bins carry which slot's data. This
implementation uses a perfectly ordinary bit-reversal permutation
*inside* the FFT kernel itself (`fft_forward_inplace`,
`src/encode_fft.cpp`) — entirely separate from, and composed with, the
`r_k`-based gather/scatter at the encode/decode level. Conflating the
two (e.g. assuming the FFT's own bit-reversal somehow already produces
CKKS slot order) would be a real implementation bug; this was checked
explicitly and is why encode/decode build their OWN `gidx`/`r` tables
rather than relying on anything the FFT kernel does internally.

## 4. Independent verification BEFORE writing any C++ (Python/numpy)

Per the governing directive's explicit instruction to verify the
mathematical convention with independent calculation before
integrating: a standalone Python prototype (`tools/` is the
established location for throwaway derivation scripts in this
project; the exact script is reproduced in this document's git history
via the commit that added it) implemented:

1. `reference_encode`/`reference_decode`: the EXACT existing
   `src/encode.cpp` formula, transcribed directly, using `numpy` only
   for elementary arithmetic (not its FFT).
2. `fft_decode`/`fft_encode`: the candidate FFT construction derived
   in §2, using `numpy.fft.fft`/`numpy.fft.ifft` as the INDEPENDENT DFT
   implementation (a completely separate codebase from this project's
   own NTT/FFT code).

**First result** (N=8,16,32,64, random complex slots): `decode`
matched the reference to `~1e-16` (machine epsilon) immediately —
confirming the gather-index derivation was correct on the first
attempt. `encode` was off by *exactly* a factor of 2 (`m_fft / m_ref ≈
2.0000` for every coefficient) — this is precisely the scaling
subtlety derived in §2 (applying `2·Delta/N` to the already-doubled
`x[j]` instead of `Delta/N`). Fixing the scale factor (from
`2·Delta/N` to `Delta/N` applied directly to the unnormalized inverse
sum) made `encode` match the reference to **zero error** (bit-for-bit
identical rounded integers) across every tested N. This is recorded
here explicitly as the one real mistake this derivation made and
caught before any C++ was written — exactly the kind of "investigate
any systematic error... before proceeding" check the governing
directive requires.

## 5. C++ implementation (`src/encode_fft.cpp`)

- `fft_forward_inplace`: a standard iterative radix-2 Cooley-Tukey DIT
  FFT (bit-reversal permutation, then `log2(M)` butterfly stages),
  matching the `X[t]=Σx[j]e^{-2πijt/M}` convention fixed in §1/§4.
  Twiddle factors are precomputed ONCE per size `M` via direct
  `cos`/`sin` calls (not iterative complex multiplication, avoiding any
  compounding rounding drift across `O(log M)` stages) and cached for
  the process lifetime — the same pattern this codebase already uses
  for its GPU root tables (`src/evalkeygen.cpp`'s `ek_dev_tab`,
  `src/encdec.cpp`'s `enc_dev_tab`).
- `fft_unnormalized_inverse`: computed via the standard conjugate
  identity `conj(FFT(conj(Z)))` (avoids writing a second FFT kernel;
  verified against `numpy`'s `ifft(Z)*M` in §4's prototype).
- `slot_idx`: the `r_k` and `gidx_k=(M-r_k)%M` arrays, cached per `N`
  (pure, read-only data depending only on `N`, identical in spirit to
  `src/encode.cpp`'s own `r[]` array).
- `encode_host_fft`/`decode_host_fft`: the scatter/gather and scale
  factors derived in §2, verified in §4, as plain, direct
  transcriptions — no additional cleverness.

**Threading**: deliberately NOT parallelized (unlike Phase 11's
`encode_host`/`decode_host`). A single FFT is an inherently *sequential*
pipeline of `O(log M)` dependent stages; splitting it across threads
would require a genuine parallel-FFT implementation for a marginal
gain, since the whole point of this round is that the FFT is already
`O(N log N)` and measured (§6) to be 31-61x faster than even the
*parallelized* O(N²) version — there is no oversubscription risk
introduced here, and no interaction with Phase 11's `std::thread` pool
in `src/encode.cpp` (that code is untouched and still parallel; this is
a wholly separate, single-threaded implementation in a new file).

## 6. Numerical correctness results (`tests/test_encode_fft_matches_reference.cpp`)

Compared against `src/encode.cpp`'s OWN (untouched) `encode_host`/
`decode_host` — a genuinely independent oracle (different algorithm,
not a different thread count of the same formula) — across N in
{16,256,1024,2048,4096,8192}, with: zero input, constant input, single
nonzero slot, alternating values, positive/negative fractional values,
random real-valued, widely-different-magnitude (spanning 10⁻³ to 10³
within one call, deliberately adversarial), complex (non-real) slots,
and a pure FFT-only round-trip sanity check.

**Decode**: matched the reference to `~1e-22`–`1e-26` absolute error at
every N and every case — pure floating-point noise, several orders of
magnitude below any tolerance this project uses anywhere.

**Encode**: matched the reference EXACTLY (zero error) for most cases.
A handful of cases (`alternating`, `pos-neg-fractional`,
`mixed-magnitude`) showed larger absolute discrepancies (up to 80 units
at N=16, mixed-magnitude case) that do NOT reduce to zero as N shrinks
and do NOT grow monotonically with N — this was investigated, not
dismissed:

- **`alternating` (+1/-1 slots)**: independently computed via `mpmath`
  at 60 decimal digits of precision (a THIRD, high-precision
  implementation of the same formula, used solely to find the true
  answer, never to validate the FFT against itself) — the true
  pre-rounding value is `~1e-47`, i.e. **exactly zero** after rounding,
  for every coefficient. Both the old and new implementations are
  independently landing within ordinary double-precision rounding
  noise of this true value of zero; their mutual difference (up to 32
  units at N=4096) is the DIFFERENCE of two near-zero floating-point
  noise floors, each individually negligible, amplified by the
  `Delta/N` scale factor applied to a near-cancellation sum. This
  matches the expected magnitude: for a sum of `~N/2` terms of
  magnitude O(1) that should cancel to ~0, the floating-point noise
  floor is `O(N·ε)` in the raw sum, becoming `O(N·ε·Delta/N) =
  O(ε·Delta)` after scaling — independent of N, consistent with the
  observed non-monotonic-in-N pattern.
- **`mixed-magnitude`**: independently computed via `mpmath` (60
  digits) for a structurally-equivalent adversarial case — the true
  value is a LARGE integer (`~±5×10¹⁵`), and both implementations land
  within a few tens of units of it (relative error `~1e-11`). The
  observed cross-implementation discrepancy is bounded by the sum's
  *conditioning* (terms spanning 1000x in magnitude), not by N.

**Derived, principled tolerance** (not loosened merely to pass):
`tol = (N + 1000) · ε · Delta`, where `1000` is this test's own chosen
worst-case magnitude spread and `ε` is `double`'s machine epsilon —
combines the N-term accumulation bound with the magnitude-conditioning
bound. This comfortably dominates every observed discrepancy (worst
case 80 vs. a bound of ≥270) while remaining `~1e-10` RELATIVE to
`Delta` — many orders of magnitude below the `1e-6` relative tolerance
this project's real-encrypted round-trip tests already use everywhere,
confirming this noise can never be cryptographically observable. All
cases pass with this tolerance; see `tests/
test_encode_fft_matches_reference.cpp`'s own comments for the full
derivation inline.

## 7. Real cryptographic correctness

`cpp_bridge/encdec_bridge.cpp`'s `gpufhe_encode`/`gpufhe_decode` — the
ACTUAL production call site every Rust caller (`codec::encode_real`/
`codec::decode`, and therefore every `real_encrypted_evalmult_*` test)
goes through — now call `encode_host_fft`/`decode_host_fft`. `src/
encode.cpp`'s `encode_host`/`decode_host` are UNCHANGED and remain
fully present, tested, and directly callable as the reference/fallback.

Full Rust suite after the swap: **38 passed, 0 failed, 1 ignored**,
identical in `--release` and debug, including `encode_decode_round_
trip_matches_input`, `encrypt_decrypt_round_trip_matches_input`, and
all four `real_encrypted_evalmult_*` tests. The real round trip's own
decoded error: `2.60e-11` (tolerance `1e-6`) — statistically
indistinguishable from Phase 11's pre-FFT value (`2.59e-11`),
confirming the FFT's own small extra error (§6) is, as predicted,
cryptographically unobservable against CKKS's inherent encryption
noise.

## 9. What remains the dominant cost, post-Phase-12

At n=8192, `encrypt_host` (17.0ms) is now the single largest
contributor to the real round trip, followed by the GPU-resident
keyswitch (2.0ms) and rescale (1.9ms) — `encrypt_host` was already
batched in Phase 11 (one upload + one batched NTT + one download per
buffer instead of 32 separate round trips) and was not touched this
round. Encode (1.16ms) and decode (0.29ms) are no longer meaningful
contributors. The clear next highest-value experiment, if performance
work continues, is profiling `encrypt_host` itself more closely (its
own internal NTT cost vs. its embedding/combine loops) — not another
pass over encode/decode, which are now solidly out of the critical
path.
