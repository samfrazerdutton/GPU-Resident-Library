# Phase 42: Performance Results — Batched `rescale_resident_raw`

## Environment

RTX 2060 Max-Q (6144 MiB, driver 595.97), CUDA 13.2, `CMAKE_BUILD_TYPE=Release`,
`CMAKE_CUDA_FLAGS` empty (no `-G`, re-verified from `CMakeCache.txt`
before trusting any number below), clean PATH applied throughout (see
`research/PHASE42_PERFORMANCE_AUDIT.md` section 2). All measurements
below use real CKKS parameters generated by OpenFHE's own HYBRID
key-switch parameter derivation (guaranteed `P>=Q_part_max`), not
synthetic/approximate moduli.

## 1. Isolated kernel-level: `rescale_resident_raw` itself (real function, not a proxy)

`bench/bench_rescale_resident_batched_vs_serial`: in-process A/B via
the `g_rescale_batched` toggle, order-alternated every repetition, 50
reps dedicated warm-up before any timed rep, 500 timed reps per depth,
CUDA-event timing around the one function call, median reported, 3
independent process runs.

| depth | towers (last) | n | Run 1 | Run 2 | Run 3 |
|---:|---:|---:|---|---|---|
| 3 | 4 (3) | 32768 | OLD 0.564ms, NEW 0.478ms, **1.18x** | OLD 0.669ms, NEW 0.518ms, **1.29x** | OLD 0.611ms, NEW 0.512ms, **1.19x** |
| 6 | 7 (6) | 32768 | OLD 1.191ms, NEW 0.436ms, **2.73x** | OLD 1.019ms, NEW 0.451ms, **2.26x** | OLD 1.032ms, NEW 0.466ms, **2.21x** |
| 10 | 11 (10) | 32768 | OLD 2.079ms, NEW 0.605ms, **3.44x** | OLD 2.477ms, NEW 0.641ms, **3.87x** | OLD 2.474ms, NEW 0.635ms, **3.89x** |

**Honest reading**: the speedup grows with `towers`, as expected (more
serial iterations collapsed into the same ~7 batched launches). At the
shallowest depth tested (3, `last=3`), the win is modest (~1.2-1.3x);
at `last=10` it is substantial (~3.4-3.9x) and highly reproducible
across 3 independent runs (tight spread). Absolute time saved at
`last=10`: ~1.6-1.9ms per call -- a real, large absolute saving, not
just a ratio.

## 2. Function-level: full EvalMult (tensor + resident relin + combine + 2x resident rescale)

`bench/bench_evalmult_resident`, N=16 concurrent chains on separate
streams, direct (non-graph) path, same `g_rescale_batched` toggle,
order-alternated, warmed up. towers=4 (depth 3, the shallowest config
this bench builds):

| Run | OLD (serial rescale) | NEW (batched rescale) | Speedup |
|---|---:|---:|---:|
| 1 | 4.252ms | 3.815ms | 1.115x |
| 2 | 4.509ms | 3.904ms | 1.155x |
| 3 | 4.445ms | 3.999ms | 1.112x |

**This is a real, measured, reproducible APPLICATION-level (full
EvalMult) speedup, not an isolated-kernel number mistaken for one.**
Modest (~11-16%) at this shallow depth because rescale is one of
several stages (tensor, relin/keyswitch, combine, rescale) and the
isolated section 1 result at `last=3` was itself only ~1.2-1.3x; the
end-to-end number is consistent with that, not inflated.

## 3. Operation-level breakdown (existing bench, re-run, confirms rescale's real weight)

`bench/bench_evalmult_e2e_breakdown` (unmodified, run as-is with the
new batched path active by default): steady-state per-stage GPU-event
medians for one `multiply_relin_rescale` call --
`keyswitch=2158.46us`, `rescale x2=732.096us`, `tensor=76.96us`,
`combine=67.424us`, full wall time `median=4403.56us`. Rescale is
~16.6% of the full operation at this config -- a meaningful, not
dominant, fraction, consistent with the modest (not dramatic)
end-to-end speedup in section 2 and with key-switching remaining the
single largest GPU-side cost (unchanged this phase, a Phase 43
candidate if further gains are sought there).

**Correctness, independently re-confirmed by this same bench** (not
just a timing run): `0/114688 mismatches` against an independent
tensor+relin+combine+rescale reference; real encrypted round-trip max
abs error `1.12912e-10` (tolerance `1e-6`) -> PASS.
`bench/bench_evalmult_cpp_vs_rust` similarly: `0/14336 mismatches`
against an independent reference.

## 4. What was NOT claimed

- No end-to-end CUDA-graph-path number is reported as an A/B, because
  toggling the flag after a graph is already captured changes nothing
  (the batched-or-serial choice is baked in at capture time) -- this
  is stated explicitly rather than silently omitted.
- No claim is made about deeper (`towers>11`) configurations beyond
  what was measured; the growth trend (section 1) is reported as a
  trend, not extrapolated into a specific predicted number for
  unmeasured depths.
- The isolated kernel speedup (section 1) and the end-to-end speedup
  (section 2) are reported as what they are -- a kernel-level number
  and an application-level number respectively -- never conflated.
